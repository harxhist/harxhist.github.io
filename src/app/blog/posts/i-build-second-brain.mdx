## For non-technical Readers

### The Problem

I have a large chunk of data that I bookkeep once every few months. This 2.5GB of semi-structured files and folders holds all my *real stuff*, the most relevant digital footprint of my life. It contains:

- Study notes, My gists, Work Logs, Meeting minutes, Daily journal, Poetry & Written articles
- Job documents, Bureaucracy stuff, GST, non-confidential financial, tax & EPF info & Invoices, Home bills, Family docs
- IDs, Credentials, Degrees, Mark sheets, Placement data, College & school history data
- Contacts, Mail takeouts, Audio recordings, Digital belongings, accounts, movies & music I prefer

Basically all my relevant data. This data can be categorized as: a. Important data that should be remembered in my own head, and b. Important data that need not be memorized but should be easily accessible.

The real problem I face these days is information overload and forgetfulness, which I want to address through data relevancy, persistence, and revision. This blog summarizes a solution where AI tackles both parts *a* and *b* using the Retrieval-Augmented Generation (RAG) framework of LLMs for better retrieval of important chunks of information.

### Arriving at a Solution

I wished to have a system where I could update/insert any raw data: such as txt, pdf, image, code, etc. into an existing knowledge base, and have that data become instantly queryable in plain English. This knowledge base would grow over time, and there should be some tool that can answer my questions by referencing it. In some sense, our brain does the same, except it also forgets old information. Once the knowledge base holds most of my data, I can also determine which information is most relevant. To optimize this, I came up with a simple solution for continuously revising and accessing important information.

### Solution is AI

The solution doesn't just depend on AI models and complex RAG framework. We also need software to store our knowledge base, back it up securely, and perfectly sync local changes with the cloud. To handle newly added files efficiently without wasting time, we used a queue-based system that completely skips any work we have already done.

#### Components of Solution

- **Gemini:** The Cloud AI "brain" used to read, translate(preprocess) raw files into LLM understandable language(embeddings), and understand all file types.

- **Pinecone:** A specialized cloud filing cabinet(vector database) built specifically for AI memory storage.

- **AnythingLLM:** The local chat app window(orchestrator) you use to interact with your knowledge base.

- **Obsidian:** The local folder (**vault**) on your laptop that holds all your raw data, where you do most of the work like taking notes.

- **Git:** A background tool used to track, back up, and sync data securely.

- **SQLite:** A tiny database manager used to maintain the active file queue.

- **Launchd:** A macOS system manager that ensures our background workers run continuously.

- **Python & Bash Scripts:** The invisible backend connective code wiring that handles the data.

Among these components only Gemini, Pinecone & GitHost is on cloud, rest all lies on your local mac machine. You only interact with **Obsidian Vault** & **AnythingLLM** in your day-to-day work.

### How it works

Think of this system as your private, efficient digital factory. Instead of you manually sorting through your files, workers handles the heavy lifting behind the scenes.

Here is exactly how a file goes from jargon to a permanent part of your AI's memory:

1. **Obsidian:** You drop or create a file in your Obsidian folder. It could be a typed note, a scanned PDF of a tax invoice, a screenshot of a chart, or a voice recording.

2. **Git & SQLite:** A background guard immediately notices you added or changed something. It notes down the file's name in a digital clipboard (the queue) so it knows there is new work to do. If you just edited an old note to fix a typo, it wisely says, _"Hey, we've already processed 99% of this file before, let's only update the change!"_ This saves massive amounts of time and computing power.

3. **Python & Gemini:** This is where the magic happens. A background worker picks up the file and evaluates it. If it's a **voice memo**, it listens to the audio and writes it down as clean text paragraphs. If it's a **screenshot**, it looks at the image, reads the text inside it, and writes a detailed description of the diagram. If it's a **scanned PDF**, it reads it page-by-page, converting messy tables and text into clean, readable formatting.

4. **AnythingLLM & Pinecone:** Once everything is turned into processed text which is understandable by AI, it is handed over to a AnythingLLM on your computer, which packages it up and ships it off to a Pinecone(vector database). This database doesn't just store words; it stores the _meaning_ behind your words(embeddings). After this, you can chat with LLM grounded in your data.

### Why Do We Need RAG & How it can solve our problem?

Before diving into the code, let's demystify the core concept.

When you ask a standard AI model (like ChatGPT or Gemini) a question about your personal files, it cannot answer because it wasn't trained on your data. You have three ways to fix this:

- **Fine-Tuning:** Training the model on your data. _Why it fails here:_ It's expensive, slow, requires massive computational power, and the model can still hallucinate details.

- **Context Window Stuffing:** Shoving all 5,000 of your files into the AI prompt every time you ask a question. _Why it fails here:_ Even with massive context windows, sending megabytes of data on every single query is slow and burns through API limits instantly.

- **RAG (The Winner):** When you ask a question, a local script searches your vault for the top 10 most relevant sentences or paragraphs, grabs only those pieces, and feeds them to the AI along with your question.

#### The Live Query Pipeline in 5 Simple Steps

1. **The Ask:** You type a question: _"What did I note down about APISIX API Gateway?"_

2. **The Vector Search:** The system converts your question into a math vector (a string of numbers representing its semantic meaning) and matches it against your processed notes stored in a **Vector Database (Pinecone)**.

3. **The Retrieval:** Pinecone returns the top 10 most relevant text chunks from your actual files.

4. **The Augmentation:** The system bundles your question and those 10 text chunks into a neat prompt package.

5. **The Generation:** **Gemini 2.5 Flash** or any LLM of choice reads the context and provides a precise answer, grounded purely in your data, complete with file citations.

### System Architecture

Let's be real, most of our relevant raw data is not entirely textual (which is the primary requirement of LLMs before embedding). Real life is messy. A typical personal vault/folder has PDF files, phone screenshots, voice memos, contacts, code, and more.

To handle this, the architecture is split into two halves: an **Ingestion/Transformation Daemon** and an **Orchestration/Query Layer**.

**The 5-Track Preprocessing Ingestion Pipeline**

The pipeline categorizes and transforms every file type into clean, searchable Markdown (`.md`) that the vector database can easily understand:

- **Track 1 — Text & Code (Mirror As-Is):** Markdown and code files (`.go`, `.py`, `.ts`, `.sql`) are read natively as UTF-8 and copied as-is.
- **Track 2 — PDFs (Gemini Native Parsing):** Instead of using fragile Python text-extraction libraries that choke on scanned images, raw PDF bytes are sent directly to the Gemini 2.5 Flash API using its native `application/pdf` renderer. It converts layouts, tables, and text into clean Markdown.
- **Track 3 — Images (Vision OCR):** Whiteboard drawings and screenshots are passed to Gemini Vision to transcribe all embedded text and generate precise technical descriptions of diagrams.
- **Track 4 — Audio (Multimodal Transcription):** Voice memos and recorded ideas are fed into Gemini's audio pipeline to produce high-fidelity, paragraph-segmented transcripts.
- **Track 5 — Binary Docs (Native Passthrough):** Word documents (`.docx`) and eBooks (`.epub`) are passed directly to the local orchestrator (AnythingLLM), which handles them natively.

This completes the preprocessing stage. Running it on a full 2.5 GB vault took 4.5 hours, but this is a one-time cost. Any subsequent changes to the vault are processed incrementally and take only a few seconds.

### Deep Dive Into the Code

Our background automation relies on two Python scripts working in tandem: a **Queue Producer** (`queue_jobs.py`) and a **Background Processing Daemon** (`transform_daemon.py`).

#### Script 1: The Incremental Queue Producer

Re-indexing thousands of files every time you fix a typo is highly inefficient. We use Git to track file changes and an SQLite database to maintain an active state of what needs processing.

This script checks my vault's Git status using `git diff-tree`, identifies which files were Added (**A**), Modified (**M**), or Deleted (**D**), and saves them into an SQLite queue using Write-Ahead Logging (WAL) for safety.

```python
def main():
    conn = init_db()
    os.chdir(OBSIDIAN_VAULT)

    # Ask Git what changed in the latest commit
    result = subprocess.run(
        ["git", "diff-tree", "-r", "--name-status", "--no-commit-id", "HEAD"],
        capture_output=True, text=True,
    )
    if result.returncode != 0:
        sys.exit(1)

    lines = result.stdout.strip().split("\n")
    for line in lines:
        if not line: continue
        parts = line.split("\t")
        status = parts[0][0]

        if status in ("A", "M"):
            enqueue_job(conn, parts[1], "PROCESS")
        elif status == "D":
            enqueue_job(conn, parts[1], "DELETE")
        elif status == "R": # File renamed
            enqueue_job(conn, parts[1], "DELETE")
            enqueue_job(conn, parts[2], "PROCESS")
    conn.close()
```

#### Script 2: The Core Processing Engine

This script runs persistently in the background. Its responsible for preprocessing the enqueued files & sending the processed output to AnythingLLM. It polls the SQLite queue for `PENDING` jobs, runs them through the correct multimodal track using the Google GenAI SDK, and updates **AnythingLLM** using its REST API.

Here is how it safely transmits deep multimodal files (like large PDFs or long audio recordings) using Gemini's File API versus lightweight inline payloads:

```python
def process_gemini(file_path: Path, mime_type: str, task_type: str, use_file_api: bool) -> str:
    prompt = PROMPTS[task_type]
    header = f"# AI-Generated {task_type} Transcript\n- **Source:** `{file_path.name}`\n\n---\n\n"
    current_model = os.getenv("GEMINI_MODEL", "gemini-2.5-flash")

    if use_file_api:
        # Crucial for large files (>5MB) like heavy PDFs or voice recordings
        uploaded = client.files.upload(
            file=file_path, config=types.UploadFileConfig(mime_type=mime_type)
        )
        try:
            res = client.models.generate_content(model=current_model, contents=[uploaded, prompt])
            text = res.text or "*[Empty Response]*"
        finally:
            client.files.delete(name=uploaded.name) # Clean up API storage space
    else:
        # Ultra-fast inline processing for small images and text snippets
        res = client.models.generate_content(
            model=current_model,
            contents=[
                types.Part.from_bytes(data=file_path.read_bytes(), mime_type=mime_type),
                prompt,
            ],
        )
        text = res.text or "*[Empty Response]*"

    time.sleep(RATE_LIMIT_SLEEP_SEC) # Protects free tier RPM limits
    return header + text
```

Once a file is transformed into Markdown, the daemon triggers an HTTP POST request to your local **AnythingLLM** instance to swap out old vector chunks for the new ones, keeping your vector database fresh without manual intervention.

### The Wiring Guide

Here is how components interact & becomes self-contained, automated system.

#### Phase 1: Connecting AnythingLLM to the Cloud

Open AnythingLLM Desktop and configure your settings:

- **AI Models:** Set both your **LLM Provider** and **Embedding Provider** to Google Gemini and input your API key.

- **Vector Database:** Create a serverless index in Pinecone. _Crucial:_ Set dimensions exactly to **3072** to match Gemini's output. Link this to AnythingLLM under the Vector Database tab.

- **Workspace:** Create a new workspace. Generate an AnythingLLM API key and paste it into your `.env` file.

#### Phase 2: Setting Up the Automation Hooks

To make this pipeline *live*, we rely on the Obsidian Git plugin's auto-sync feature. Here is the invisible chain reaction that happens completely in the background:

- **The Trigger:** Whenever the Obsidian Git plugin automatically backs up your vault, that commit action fires off a built-in Git alarm called a `post-commit` hook.

- **The Check:** We wire this hook to instantly wake up our `queue_jobs.py` script.

- **The Queue:** Instead of blindly scanning our entire vault and wasting computing power, the script smartly looks at the latest Git diff to see exactly which files were just created, edited, or deleted. It then drops only those fresh files into a waiting line (our SQLite database queue), queuing them up for the AI daemon to transform.

This means our system only ever processes the exact notes you are working on right now, making it lightning-fast!

#### Phase 3 : Daemonizing with macOS launchd

Deploy the Python engine as a headless, persistent background service.

**1. Configuration (`.plist`)** We define the daemon's behavior via an XML property list in `~/Library/LaunchAgents/`:

- **Execution Setup:** Set the absolute paths for the Python executable and your target script (`ProgramArguments`).

- **Always On & Staying Alive:** Guarantee high availability by instructing macOS to start the program automatically upon login (`RunAtLoad`) and actively keep it running by restarting it if it exits (`KeepAlive`).

- **Keeping Records:** Because the program runs invisibly, capture its activity by routing execution streams (`StandardOutPath` / `StandardErrorPath`) to local `.log` files. This allows you to easily check what it has been doing behind the scenes.

**2. Activation & Deployment** Use built-in macOS tools to verify your instructions are correct and officially turn on the background task:

- **Validate:** Run `plutil -lint` to verify XML syntax and catch errors before deployment.

- **Register:** Run `launchctl load` to inject the instructions into your user's `launchd` session.

- **Execute:** Run `launchctl start` to immediately trigger the daemon without requiring a system restart.

### Hard-Earned Debugging Lessons

#### Bug 1: The Vector Store Dimensional Clash

- **The Problem:** Initial test queries crashing out with: `vector dimension 3072 does not match index dimension 768`.

- **The Fix:** Standard AI models often use 768 or 1536 dimensions. However, Google's native embedding engine default is a robust 3072 dimensions. If your Pinecone index was built under alternative presumptions, delete the index and recreate it at exactly **3072** dimensions.

#### Bug 2: The Ghost Files Drop

- **The Problem:** Configuration dotfiles (`.gitignore`) or infrastructure scripts (`Makefile`) vanish during transfer layers because they lack typical extensions.

- **The Fix:** Implement an explicit fallback dictionary in your code (`EXTENSIONLESS_TEXT_NAMES`) to append pseudo `.txt` extensions onto naked system configuration elements during parsing loops.
